# 电商 AI 智能客服与业务查询助手 产品需求文档

版本：v1.0 评审稿  
日期：2026-10-26  
作者：周玉冰（需求材料由本人提供，本文据现有资料整理）  
用途：项目复盘、产品方案评审及后续开发拆解。本文描述目标需求，不等于全部功能已上线。

## 1. 背景与问题

电商客服需要同时处理商品知识和订单、库存、物流等动态查询。静态问答不能代表实时业务状态，退款和投诉还需要人工审核。产品按咨询类型协调知识检索、工具查询与人工处理。

## 2. 依据与当前边界

项目功能来源于用户简历；当前作品集中“问舟”页面为本次制作的前端交互原型，使用示例数据，未连接模型、真实 OMS、库存或物流接口。原型中的统计数字不能作为业务成果。

## 3. 目标用户与任务

| 用户 | 使用任务 | 期望结果 |
| --- | --- | --- |
| 消费者 | 咨询商品和订单售后 | 获得清楚可靠的答复与处理进展 |
| 人工客服 | 接管复杂问题 | 快速了解诉求及已有查询结果 |
| 客服运营 | 维护知识和分流规则 | 控制答复质量并定位失败链路 |

## 4. 产品目标与范围

覆盖商品、订单、库存、物流和售后五类咨询；首版工具以只读查询为主，退款与订单变更通过人工审核。

**首版范围外：**不让模型直接生成业务状态、不绕过订单归属验证、不自动退款或修改库存。前端原型不承诺已有后端服务。

优先级：P0 为首版必须闭环；P1 在 P0 质量通过后实施。具体工期需结合接口、数据与资源评估。

## 5. 核心用户流程

客户发起咨询 → 意图识别 → 澄清必要标识 → 商品知识走 RAG、动态状态走工具查询 → 生成有依据的答复 → 退款退货或投诉收集必要材料 → 生成人工工单 → 客服接管并确认关键操作 → 返回结果。

## 6. 功能需求

| 编号 | 功能 | 优先级 | 行为与约束 | 验收要点 |
| --- | --- | --- | --- | --- |
| 04-01 | 意图识别与分流 | P0 | 识别五类咨询；多意图问题拆分处理，缺少订单或商品标识先追问。 | 无法判定的意图进入澄清或人工入口，不盲目调用接口。 |
| 04-02 | 商品知识回答 | P0 | 检索有效商品与售后政策，引用适用版本和片段。 | 政策问题附依据；参数、优惠与保修承诺不得超出资料。 |
| 04-03 | 动态业务查询 | P0 | 通过结构化工具查询订单、SKU 库存和物流；先完成用户身份及资源归属校验。 | 答复使用接口实际字段，显示查询时间；超时不回退为虚构状态。 |
| 04-04 | 人工接管 | P0 | 为退款、退货、投诉和低证据问题生成摘要，保留诉求、已收集信息、查询结果和待办。 | 接管后 AI 停止自动发出业务结论；客户能看到已转交状态。 |
| 04-05 | 客服工作台 | P0 | 展示会话队列、聊天、业务信息与接管状态，支持人工回复。 | 会话切换不串客户或订单；流式回答保留完成与中断标记。 |
| 04-06 | 质量复核 | P1 | 按意图、失败工具、转人工原因和负面反馈检索会话。 | 回放保留工具版本与时间，敏感字段默认脱敏。 |

## 7. 业务规则

1. 静态商品说明与实时订单数据有不同来源；模型不得覆盖工具返回的事实。
2. 订单查询必须鉴权并核验归属，只有订单号不代表有查看权限。
3. 退款等写操作需要人工确认与幂等键，超时后先查状态再决定是否重试。
4. 相同会话由单一处理者主导；人工接管期间 AI 只提供草稿或辅助信息。
5. 外部文本和工具返回中的指令不能改变授权和调用规则。

## 8. 信息与状态设计

**核心对象：**Conversation：客户 ID、意图、当前处理者、状态；Message：角色、正文、流式状态；ToolCall：工具、脱敏参数、结果摘要、错误码、耗时；Ticket：诉求、证据、待办、负责人、处理状态；KnowledgeSource：来源、版本、片段；Audit：接管与人工确认记录。

**状态流转：**会话：待识别 → 待澄清／AI 处理中 → 已解决／待人工 → 人工处理中 → 已关闭；工具：待调用 → 调用中 → 成功／失败／超时；工单关闭需有处理结果。

界面应区分加载、空数据、失败、部分成功和完成状态。成功提示必须来自对应数据写入或服务结果，不能只根据按钮点击生成。

## 9. 异常处理

| 场景 | 处理要求 |
| --- | --- |
| 客户身份或订单归属校验失败 | 不返回订单细节，引导核实身份或人工处理 |
| 库存或物流服务不可用 | 说明暂时无法查询，保留已完成步骤，不编造结果 |
| 流式响应中断 | 标记未完成，允许继续；不能把部分答案视为处理完成 |
| 人工接管无人响应 | 显示排队状态与业务方配置的服务时间，不虚构等待分钟数 |
| 同一请求重复到达 | 复用查询或工单关联，避免重复创建与重复执行 |

## 10. 质量与数据要求

- 访问与隔离：服务端或扩展本地按实际身份与权限控制数据；会话、任务和用户之间不得串数据。
- 可靠性：为操作保留稳定标识与版本；重试、刷新和恢复不重复创建核心记录；失败原因可定位。
- 性能：先记录代表性数据规模下的加载、任务耗时及失败分布，再确定容量与响应预算；不虚构性能承诺。
- 可用性：主要操作可用键盘完成，颜色之外提供文字状态；表格在窄屏可横向滚动，不能截断关键操作。
- 可追溯性：记录请求或任务 ID、数据与规则版本、关键状态变化及脱敏错误；不在日志保存密钥或不必要的敏感正文。
- 数据生命周期：提供按权限查看、删除或归档的能力；实际保留期限、备份和恢复策略在上线前确认。

## 11. 指标与评测

意图准确率需在标注测试集按五类及未知类分别统计；任务完成率以查到所需信息或完成可核实交接为准，不能将任意回答计作完成；延迟分别记录首字、工具调用与整轮完成 P50/P95。简历中“100+ 用例、≥95% 意图准确率、≥90% 完成率、≤10s 平均响应”需补原始测试报告后作为历史结果展示；原型不验证这些指标。

指标评测应记录：数据来源、样本数、标注准则、版本、运行环境、测试日期、分子分母及失败案例。业务效果与系统测试结果分开报告。

## 12. 验收场景

- [ ] AC-01：五类核心问题分别路由至对应流程，缺标识问题先澄清。
- [ ] AC-02：订单不存在、无权限、服务超时分别返回可辨别结果。
- [ ] AC-03：物流答复与模拟接口结果一致且带查询时间。
- [ ] AC-04：退款诉求生成待人工工单而非显示退款成功，接管后 AI 不再自动答复。
- [ ] AC-05：会话切换、重复请求与服务恢复不造成跨用户数据泄露或重复工单。

## 13. 迭代与发布条件

1. 需求与数据确认：确认用户、支持范围、资料权限、依赖接口与未决问题；确定首版 P0。
2. 方案与原型：走通正常、异常及恢复流程；业务方核对术语、状态与关键规则。
3. 端到端实现：优先完成一条可验证主链路，再扩展场景；记录模拟与真实依赖的差别。
4. 试用验收：按上述场景逐条保留结果，修复阻断问题，再组织受控试用。
5. 复盘迭代：根据失败分类和用户反馈安排 P1，更新文档版本与交付状态。

发布前至少满足：P0 验收通过；访问与数据隔离通过；关键失败可恢复；已知限制可见；交付文档说明实际验证范围。

## 14. 待确认事项

- 实际身份系统、工单系统与接口契约，模拟和真实环境如何隔离。
- 转人工触发条件、服务时间、工单归属及升级机制。
- 订单数据与会话日志保留期限、访问角色及脱敏要求。
