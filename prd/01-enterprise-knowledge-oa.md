# 企业知识问答与 OA 流程助手 产品需求文档

版本：v1.0 评审稿  
日期：2026-10-26  
作者：周玉冰（需求材料由本人提供，本文据现有资料整理）  
用途：项目复盘、产品方案评审及后续开发拆解。本文描述目标需求，不等于全部功能已上线。

## 1. 背景与问题

企业制度、产品资料和 OA 办理说明分散在多个文档中。员工即使找到制度，也可能无法判断适用条件和下一步操作。产品将知识查询与办理指引放在统一对话入口中。

## 2. 依据与当前边界

用户提供了饭卡充值、清洁规范、餐厅开放时间和请假操作指引截图；简历描述了 RAG 检索与 Coze 工作流。截图能说明问答界面与回答组织方式，不能单独证明检索效果、权限隔离或真实审批执行能力。

## 3. 目标用户与任务

| 用户 | 使用任务 | 期望结果 |
| --- | --- | --- |
| 员工 | 查询制度、产品知识和办理步骤 | 找到适用答案及依据，知道下一步去哪里办理 |
| 制度与知识管理员 | 维护有效文档、检查错误回答 | 知识更新可追踪，问题能回溯至来源 |
| 流程负责人 | 确认流程适用条件与入口 | 员工按正确路径办理，减少重复解释 |

## 4. 产品目标与范围

首版提供制度与产品问答、来源定位、OA 办理指引和反馈闭环；审批申请由用户在现有系统提交。

**首版范围外：**首版不直接批准请假、修改考勤或代替有权限的审批人；不承诺所有文档类型均可解析，也不把自然语言回答视为制度原件。

优先级：P0 为首版必须闭环；P1 在 P0 质量通过后实施。具体工期需结合接口、数据与资源评估。

## 5. 核心用户流程

管理员导入并审核知识 → 员工提问 → 判断知识查询或流程指引 → 按权限检索并重排 → 组织答案及来源 → 员工查看步骤或追问 → 反馈错误 → 管理员修订知识。

## 6. 功能需求

| 编号 | 功能 | 优先级 | 行为与约束 | 验收要点 |
| --- | --- | --- | --- | --- |
| 01-01 | 知识导入与版本 | P0 | 管理员上传支持格式的制度或产品资料，预览解析结果，配置业务分类、生效时间及可见范围后发布。解析失败不得进入检索库。 | 文档状态为待解析、待审核、已发布、已停用或失败；停用内容不再用于新回答。 |
| 01-02 | 有依据的问答 | P0 | 员工提交问题后检索授权文档；回答显示主题、核心内容和来源。来源至少包含文档名、版本、片段定位。 | 点击来源能定位支持该结论的片段；没有支持证据时说明无法确认，不拼接不存在的制度。 |
| 01-03 | 流程指引 | P0 | 识别请假等办理意图，先询问必要条件，再展示所需材料、入口与操作顺序。 | 未知适用条件时先澄清；指引与实际提交动作分开，未经系统结果确认不得显示办理成功。 |
| 01-04 | 追问与纠错 | P0 | 在当前会话内保留必要上下文；员工可对回答提交不准确、过期或无法办理反馈。 | 追问不串到其他人的会话；反馈关联问题、回答与知识版本。 |
| 01-05 | 知识运营 | P1 | 管理员按高频问题、未命中问题和负面反馈筛选，创建待补充知识清单。 | 报表可回到具体问题，个人信息按权限显示。 |

## 7. 业务规则

1. 权限过滤必须发生在检索返回内容和生成答案之前；前端隐藏文档不能代替服务端鉴权。
2. 新旧制度冲突时，优先采用已审核且适用的有效版本；无法判断时提示冲突并给出联系人。
3. 文档中的指令视为业务资料，不允许覆盖系统规则或授权范围。
4. 多轮会话中的部门、岗位和办理条件可由用户纠正；修正后重新判断适用流程。

## 8. 信息与状态设计

**核心对象：**Document：文档 ID、标题、分类、版本、有效期、权限范围、解析状态；Chunk：片段 ID、文档 ID、页码或段落、正文；Answer：会话 ID、问题、回答、引用片段、生成状态；Guide：流程 ID、适用条件、所需材料、入口；Feedback：类型、关联回答、处理状态。

**状态流转：**知识：待解析 → 待审核 → 已发布 → 已停用；问答：待处理 → 检索中 → 生成中 → 已完成／证据不足／失败；流程指引：条件待补充 → 可展示步骤。

界面应区分加载、空数据、失败、部分成功和完成状态。成功提示必须来自对应数据写入或服务结果，不能只根据按钮点击生成。

## 9. 异常处理

| 场景 | 处理要求 |
| --- | --- |
| 文档解析失败 | 标明文件与失败原因，允许重新上传；不显示导入成功 |
| 检索无结果或置信不足 | 说明未找到可靠依据，建议补充问题或联系负责人 |
| 来源失效或无访问权限 | 不泄露片段正文；展示可访问的替代依据或联系入口 |
| 模型或检索超时 | 保留问题并允许手动重试；避免重复生成反馈工单 |

## 10. 质量与数据要求

- 访问与隔离：服务端或扩展本地按实际身份与权限控制数据；会话、任务和用户之间不得串数据。
- 可靠性：为操作保留稳定标识与版本；重试、刷新和恢复不重复创建核心记录；失败原因可定位。
- 性能：先记录代表性数据规模下的加载、任务耗时及失败分布，再确定容量与响应预算；不虚构性能承诺。
- 可用性：主要操作可用键盘完成，颜色之外提供文字状态；表格在窄屏可横向滚动，不能截断关键操作。
- 可追溯性：记录请求或任务 ID、数据与规则版本、关键状态变化及脱敏错误；不在日志保存密钥或不必要的敏感正文。
- 数据生命周期：提供按权限查看、删除或归档的能力；实际保留期限、备份和恢复策略在上线前确认。

## 11. 指标与评测

检索命中率 = 标注问题中召回正确来源的问题数 / 可回答标注问题数；引用支持率 = 被来源直接支持的抽检结论数 / 抽检结论数；端到端延迟记录 P50、P95；另外统计未解决问题与纠错处理时长。简历中的 ≥90% 命中率、≤15s 平均响应和 ≥30% 周期缩短作为历史自述，发布前需补测试集、样本量、时间窗口与对照口径，本文不将其写成已验证结果。

指标评测应记录：数据来源、样本数、标注准则、版本、运行环境、测试日期、分子分母及失败案例。业务效果与系统测试结果分开报告。

## 12. 验收场景

- [ ] AC-01：授权用户询问饭卡充值时，回答覆盖渠道与适用餐厅，且引用对应制度片段。
- [ ] AC-02：无权限用户不能通过问答或来源链接获得受限文档内容。
- [ ] AC-03：请假条件不完整时先澄清；页面不出现未经真实接口确认的“请假成功”。
- [ ] AC-04：知识版本停用后，新会话不再引用该版本；历史回答仍标明其原始版本。
- [ ] AC-05：无依据问题与模型超时分别进入证据不足和失败状态，用户可辨别。

## 13. 迭代与发布条件

1. 需求与数据确认：确认用户、支持范围、资料权限、依赖接口与未决问题；确定首版 P0。
2. 方案与原型：走通正常、异常及恢复流程；业务方核对术语、状态与关键规则。
3. 端到端实现：优先完成一条可验证主链路，再扩展场景；记录模拟与真实依赖的差别。
4. 试用验收：按上述场景逐条保留结果，修复阻断问题，再组织受控试用。
5. 复盘迭代：根据失败分类和用户反馈安排 P1，更新文档版本与交付状态。

发布前至少满足：P0 验收通过；访问与数据隔离通过；关键失败可恢复；已知限制可见；交付文档说明实际验证范围。

## 14. 待确认事项

- 实际支持的文件格式、文档权限来源和知识更新责任人。
- OA 平台是否只提供链接，哪些流程具备可调用接口及授权。
- “流程处理周期”的起止时间与对照组如何定义。
