# AI 求职辅助浏览器插件 产品需求文档

版本：v1.0 评审稿  
日期：2026-10-26  
作者：周玉冰（需求材料由本人提供，本文据现有资料整理）  
用途：项目复盘、产品方案评审及后续开发拆解。本文描述目标需求，不等于全部功能已上线。

## 1. 背景与问题

求职者在 BOSS 直聘浏览和沟通岗位时，需要反复整理 JD、核对简历并维护进度。页面跳转容易造成上下文丢失，点击沟通也不一定意味着发送成功。产品以可靠记录为基础，再提供有证据的岗位匹配。

## 2. 依据与当前边界

用户提供了求职台账与 Excel 导出截图；工作区已有《求职记录助手 PRD》v0.8、boss-ledger 代码和测试配置。简历还描述了匹配分析与人工核对后的沟通队列。本稿是组合产品需求，不把早期台账版本未包含的 AI 功能写成已交付；具体实现状态须对照当前构建验证。

## 3. 目标用户与任务

| 用户 | 使用任务 | 期望结果 |
| --- | --- | --- |
| 求职者 | 记录岗位、分析匹配、跟进联系 | 减少重复整理并保留真实沟通状态 |

## 4. 产品目标与范围

P0 为当前浏览器本地岗位台账与可靠记录；P1 为可配置模型的简历匹配和证据校验。可选沟通队列必须经过独立验证后启用。

**首版范围外：**不读取未加载历史消息，不采集账号密码或登录凭据；不默认开启采集，不绕过登录验证，不承诺平台所有页面都能识别。云同步、手机采集与商店上架不纳入本轮。

优先级：P0 为首版必须闭环；P1 在 P0 质量通过后实施。具体工期需结合接口、数据与资源评估。

## 5. 核心用户流程

安装并阅读数据说明 → 手动开始记录 → 浏览岗位并暂存已展示内容 → 用户沟通 → 核验发送结果与岗位归属 → 正式登记或待确认 → 手动核对 → 查看匹配依据 → 更新进度 → 导出或备份。

## 6. 功能需求

| 编号 | 功能 | 优先级 | 行为与约束 | 验收要点 |
| --- | --- | --- | --- | --- |
| 03-01 | 全局记录开关 | P0 | 默认关闭；用户开启后作用于当前浏览器配置中的目标网站标签页。停止后停止新读取与监听。 | 重启浏览器或重载扩展后保持关闭；关闭侧边栏不等于停止记录。 |
| 03-02 | 岗位快照与关联 | P0 | 提取当前已展示的公司、岗位、链接、JD 与采集时间，跳转前暂存并关联标签页与动作。 | 未展开 JD 标记不完整；不能根据最近浏览的岗位猜测会话归属。 |
| 03-03 | 登记与待确认 | P0 | 发送成功证据和岗位身份均可靠时正式登记；只有点击、归属不明或结果未知进入待确认。 | 待确认不计入已登记数；用户可核对登记、关联已有岗位或忽略。 |
| 03-04 | 去重与进度维护 | P0 | 优先按岗位稳定 ID 或有效链接去重；保留备注、进度与 JD 版本。 | 同公司同名岗位不能仅按名称合并；再次沟通不降低面试等人工设置进度。 |
| 03-05 | 导出与备份 | P0 | Excel 包含岗位及 JD；用户可选择另附待确认工作表。JSON 用于备份与恢复。 | 导入失败不破坏现有数据，重复导入不重复记录，导入后记录开关保持关闭。 |
| 03-06 | 简历匹配 | P1 | 按城市、薪资及排除词筛选；结合简历与 JD 原文生成优势、缺口及引文。 | 所有引文校验存在于源文本；证据缺失明确标记，不能替用户编造经历。 |
| 03-07 | 人工核对后沟通队列 | P1 | 仅使用用户逐项确认的岗位及文案，设置操作预算与单任务状态。 | 资料变更需要重新核对；未知结果暂停，禁止自动重发；不影响用户手动使用网站。 |

## 7. 业务规则

1. 岗位主记录、沟通事件和 JD 版本分开保存，一次沟通事件不应生成多个岗位。
2. 旧消息加载、手机同步、进入聊天页面均不能直接视为本机新发送成功。
3. 自动确认与用户确认分别记录来源；本地写入成功后才能提示“已记录”。
4. 采集关闭期间不后台补 JD；用户可手动粘贴内容。
5. 模型分析默认不发送数据，用户配置服务并主动发起后才传输必要文本；密钥不得写入导出或日志。

## 8. 信息与状态设计

**核心对象：**Job：岗位 ID、来源链接、公司、岗位、城市、薪资、当前进度；JDVersion：正文、采集时间、完整性；ContactEvent：动作、观察时间、成功依据、确认来源；Pending：原因、关联候选、核对状态；Match：简历版本、JD 版本、规则结果、引文校验；QueueTask：用户确认版本、预算、状态。

**状态流转：**事件：暂存 → 核验中 → 已确认／待确认／明确失败；进度与事件独立维护。队列：待核对 → 待执行 → 执行中 → 成功／失败／结果未知暂停／用户取消。

界面应区分加载、空数据、失败、部分成功和完成状态。成功提示必须来自对应数据写入或服务结果，不能只根据按钮点击生成。

## 9. 异常处理

| 场景 | 处理要求 |
| --- | --- |
| 只有点击没有成功依据 | 进入待确认，不假报失败或成功 |
| 页面结构变化或权限失效 | 停止当前识别并提示手动登记，不扩大到所有网站权限 |
| 本地存储写入失败 | 保留可恢复内容并提示失败，不增加已登记数量 |
| 模型限流或输出无效 | 保留原岗位与简历，标记分析失败；不把失败分析用于执行 |
| 账号变化或验证码出现 | 停止采集或队列，等待用户正常处理，不自动绕过 |

## 10. 质量与数据要求

- 访问与隔离：服务端或扩展本地按实际身份与权限控制数据；会话、任务和用户之间不得串数据。
- 可靠性：为操作保留稳定标识与版本；重试、刷新和恢复不重复创建核心记录；失败原因可定位。
- 性能：先记录代表性数据规模下的加载、任务耗时及失败分布，再确定容量与响应预算；不虚构性能承诺。
- 可用性：主要操作可用键盘完成，颜色之外提供文字状态；表格在窄屏可横向滚动，不能截断关键操作。
- 可追溯性：记录请求或任务 ID、数据与规则版本、关键状态变化及脱敏错误；不在日志保存密钥或不必要的敏感正文。
- 数据生命周期：提供按权限查看、删除或归档的能力；实际保留期限、备份和恢复策略在上线前确认。

## 11. 指标与评测

正式登记准确率 = 抽检中动作与岗位均正确的正式记录数 / 抽检正式记录数；漏记率只针对事先定义的可识别场景统计；另统计重复记录率、待确认比例、原文引文有效率、备份恢复成功率。原有“19 项规则测试”只代表该版本用例通过，不代表全部真实网站路径兼容。

指标评测应记录：数据来源、样本数、标注准则、版本、运行环境、测试日期、分子分母及失败案例。业务效果与系统测试结果分开报告。

## 12. 验收场景

- [ ] AC-01：默认安装与重启后不读取目标网站内容；用户开启后才记录。
- [ ] AC-02：两标签页同时操作不会串岗位，重复反馈只处理一次。
- [ ] AC-03：结果未知时出现在待确认列表，已登记统计不增加。
- [ ] AC-04：重复导入同一备份不增加重复项；包含公式前缀的外部文本在 Excel 中不作为公式执行。
- [ ] AC-05：修改简历或 JD 后原匹配标记为旧版本；引文不存在时显示证据校验失败。
- [ ] AC-06：可选队列遇未知结果立即暂停，刷新或恢复不会自动重新发送。

## 13. 迭代与发布条件

1. 需求与数据确认：确认用户、支持范围、资料权限、依赖接口与未决问题；确定首版 P0。
2. 方案与原型：走通正常、异常及恢复流程；业务方核对术语、状态与关键规则。
3. 端到端实现：优先完成一条可验证主链路，再扩展场景；记录模拟与真实依赖的差别。
4. 试用验收：按上述场景逐条保留结果，修复阻断问题，再组织受控试用。
5. 复盘迭代：根据失败分类和用户反馈安排 P1，更新文档版本与交付状态。

发布前至少满足：P0 验收通过；访问与数据隔离通过；关键失败可恢复；已知限制可见；交付文档说明实际验证范围。
